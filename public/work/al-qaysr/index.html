The problem

A restaurant in Beirut needed a fast menu guests could open from a QR code at the table, with separate dine-in and take-away prices, that any host could serve without a database.

What I built

  • Two menus from one list: Take Away and Tables, each with its own prices, from a single entry per dish.
  • Fast browsing: search, a sticky section rail and a details sheet for every dish.
  • Ordering on WhatsApp: a basket builds one ready-to-send message with quantities, prices and the total. No server, no payment step.
  • An Arabic interface that switches before the first paint, so it never flashes left to right.
  • Search-engine data: the restaurant and its full menu in schema.org JSON-LD, with every dish priced for its menu.
  • Printable QR codes for the tables, and a hidden owner panel to edit dishes, prices and photos.

How it works

The whole menu is one JSON file baked into a static Next.js export, so the public site is plain HTML. Each dish carries a prices object, and which menus it appears on follows from that. The owner’s edits go to Supabase and reach the site by rebuilding it.

menu.json · one dish, two menus"prices": { "TABLES": 22.22, "TAKE_AWAY": 16.66 }  // both, different price
"prices": { "TABLES": 5 }                          // dine-in only
"prices": { "TAKE_AWAY": 20 }                       // take-away only

Key decisions

  • Static on purpose: there is no database at runtime, so any host can serve it and there is nothing to keep online.
  • A database outage can’t take the menu down: the build pulls the latest menu and falls back to the committed file if the database is unreachable.
  • A hidden URL isn’t security: the owner panel is protected by sign-in and the database’s row-level security.
  • The restaurant’s words stay its own: dish names are shown as written, not machine-translated, and any description written for an empty dish is flagged for the owner to check.
